# 0006: The Mac app carries the engine, and its tests run two daemons

Date: 2026-11-16

## Context

Phase 4 needs a Mac app a person can use without a terminal. The engine
is Go; the app is Swift. How they relate decides what the app can be
trusted to do, and what CI can verify without GUI automation.

## Decision

- The app bundle carries the engine binary at
  `Contents/MacOS/synk-daemon` and is its only writer. The app talks to
  it through the local API with the token in the data folder, exactly
  like the CLI. The name is `synk-daemon`, not `synk`: on a
  case-insensitive volume, a file named `synk` next to the app binary
  `Synk` overwrites it (found the hard way; the copy phase destroyed
  the app once).
- If a daemon is already serving the data folder, the app uses it
  instead of starting its own, so `synk serve` and the app agree.
- The app tests don't mock the API: `apps/tests` spawns two real
  daemons on temporary data folders, pairs them through the client's
  parsed QR link, syncs files both ways, and checks versions, restore,
  pause, resume, and the event stream. `make app-test` runs them; CI
  runs it on macOS after building `bin/synk`.
- The Xcode project is generated by XcodeGen from `project.yml` and is
  git-ignored; `project.yml` is the checked-in truth.
- Builds are ad-hoc signed so they run where they were built. A
  distributable Developer ID build is the maintainer's step.

## Consequences

- Every API change the app can see is caught by tests that run the
  real daemon, not a stub — the client can't drift from the server
  without a red test.
- The app needs no sandbox for 0.1.0 (it reads the token file and
  spawns the daemon). If the app ever ships in the Mac App Store, the
  daemon must move behind an XPC service with its own entitlements;
  the local API boundary already gives that split a seam.
- CI needs macOS with Xcode and `brew install swiftlint xcodegen`,
  which is slower than the Go jobs; the changes gate keeps it off
  docs-only runs.
