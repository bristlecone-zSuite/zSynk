- 2026-11-17: vault-at-rest encryption landed (decision 0016). The vault and the blob store seal under a passphrase: per-file AES-256-GCM envelopes (1 MiB chunks, a random 32-byte base per file, chunk nonce `SHA-256(base || index)[:12]` so one key never reuses a nonce), Argon2id key derivation, and a `keycheck.json` (salt + sealed check value) that fails a wrong passphrase with `ErrVaultLocked` before anything is read. Sealed and plain files coexist — a file is sealed iff it carries the magic — so a crash mid-migration leaves a mixed store both modes open; enabling seals in place, file by file, atomically. In an encrypted vault quarantined content is stored under a fixed label so names don't sit on disk. The blob store takes a `Sealer` (defined in the vault package, so the dependency points one way); the content hash stays the plaintext hash and every read still verifies it. Surface: `synk encrypt [--off] [--passphrase PASS]` (prompts twice when the flag is omitted), `POST /v1/config/encryption/enable|disable` (403 on a locked vault, 400 on an empty passphrase or a state mismatch), `SYNK_VAULT_PASSPHRASE` for daemons, `vaultEncrypted` in the status. Tests at six layers: cipher (round-trip, tamper, multi-chunk), vault (enable/disable/mixed/wrong-passphrase), blob (sealed/plain coexistence, seal-at-rest), engine (two-node round trip with the needle absent from disk), API and CLI. `golang.org/x/crypto` and `golang.org/x/term` are the new dependencies, recorded in the decision.
